# UC-09 · Nhật ký chuyến đi và tóm tắt sau chuyến

> Đặc tả nháp · v0.3 · 24/10/2026 · Owner: P3 · Mảng K: **K1, K2, K4** · Điểm đến: **Huế** · Phase 2
> Bám `AGENTS.md` và `agent/db/schema.sql` (nhóm H: `trip_events`, `journals`; đọc `itinerary_slots`, `trip_profiles`).

## 1. Mục tiêu

Từ sự kiện ứng dụng ghi trong chuyến đi, agent sinh **nhật ký ngày** (đi đâu, ăn gì, chi bao nhiêu, khác kế hoạch ở
đâu) và **tóm tắt chuyến** (tổng chi so với ngân sách, điểm nổi bật, gợi ý lần sau) bằng tiếng Việt và tiếng Anh.
Nguyên tắc: **code quyết định sự thật, LLM chỉ quyết định cách kể** – mọi con số do code tính, mọi câu truy được về `event_id`.

## 2. Phạm vi

| Trong phạm vi | Ngoài phạm vi |
|---|---|
| Sự kiện: slot đã đi / bỏ, ghi chú, metadata ảnh, chi tiêu, điều chỉnh | Lưu file ảnh, lưu toạ độ (schema chỉ có `poi_id`) |
| Nhật ký ngày, tóm tắt chuyến song ngữ, chuyến 1–5 ngày | Quy đổi ngoại tệ (người dùng nhập VND) |
| Điều chỉnh thủ công từ nút báo sự cố của PWA | UC-04, UC-05 (nhóm không nộp) |

## 3. Luồng (`runs.uc = 'UC-09'`)

- **Ghi sự kiện:** PWA → API (người dùng lấy từ session) → lọc riêng tư (bỏ GPS ảnh, vị trí → `poi_id`, che chuỗi toạ độ
  trong ghi chú) → `INSERT OR IGNORE` theo `event_id` do app sinh → `trip_events`. `slot_done`/`slot_skipped` cập nhật
  `itinerary_slots.progress` (`planned | done | skipped`). Ghi qua hàm mới trong `agent/db/repo.py` (ví dụ `add_trip_event`).
- **Kết thúc ngày** → nhật ký ngày; **kết thúc chuyến** → tóm tắt chuyến. Graph cấp chuyến chạy song song từng ngày
  (`Send`), subgraph ngày chỉ trả khoá `journals`; checkpointer SQLite để chạy tiếp khi ứng dụng tắt.

| Bước (1 ngày) | Việc chính |
|---|---|
| B1 | Lấy sự kiện của ngày; ngày trống → nhật ký mẫu `is_empty`, không gọi LLM |
| B2 | Tool cộng chi tiêu (số nguyên) và so kế hoạch (`itinerary_slots` của lịch trình `approved`/mới nhất) với `slot_done`/`slot_skipped` |
| B3 | Nén log: mỗi sự kiện 1 dòng, giữ `event_id`; ngày vượt `T_max` thì tóm tắt theo buổi trước (tóm tắt theo tầng) |
| B4 | `agent_loop(...)` với model Pydantic `DailyJournalDraft`; số tiền/giờ chỉ qua placeholder (`{{money:day_total}}`) |
| B5–B6 | Validator (mục 7); sai thì sinh lại kèm lỗi, tối đa 2 lần; hết lượt giữ phần hợp lệ, gắn cờ `degraded` |
| B7 | Code thay placeholder bằng số, lưu `journals` (`total_spent_vnd` do code cộng, `tokens_before`, `tokens_after`) |

Ranh giới ngày: 04:00 giờ Việt Nam (bữa ăn 00:30 thuộc ngày trước); chi phí trước ngày khởi hành ghi `day_index = 0`,
chỉ tính vào tổng chuyến.

## 4. Dữ liệu (đúng `agent/db/schema.sql`)

- **trip_events**: `event_id`, `trip_id`, `occurred_at`, `day_index`, `event_type` (`slot_done`, `slot_skipped`, `note`,
  `photo_meta`, `expense`, `adjustment`), `slot_id` → `itinerary_slots` (dạng `'<itinerary_id>:d1-s2'`), `poi_id` → `pois`,
  `amount_vnd ≥ 0`, `payload` (JSON), `created_by` (`user | system`).
- **journals**: `journal_id`, `trip_id`, `scope` (`day | trip`), `day_index` (NULL khi `scope = 'trip'`, schema có CHECK),
  `lang`, `content` (JSON DailyJournal / TripSummary), `event_ids` (JSON), `total_spent_vnd`, `tokens_before`,
  `tokens_after`, `run_id`, `created_at`. Tóm tắt chuyến lưu 2 dòng `lang = vi` và `lang = en` cùng `run_id`.
- Đọc thêm: `trip_profiles` (ngân sách `budget_total_vnd`, ngôn ngữ), `itinerary_slots` (kế hoạch, `cost_vnd` NULL = chưa có giá).
- **Câu hỏi mở (cần PR nhãn `contract` nếu đổi schema):** nhóm chi tiêu (lưu trú/ăn/vé/di chuyển) để trong `payload`
  hay thêm cột; sửa khoản chi bằng sự kiện mới loại `adjustment` (enum hiện chưa có `event_voided`) hay cho sửa trực tiếp.

## 5. Schema đầu ra (Pydantic, đặt trong `agent/schemas` qua PR `contract`)

```python
class JournalItem(BaseModel):
    text: str                                   # có thể chứa placeholder
    event_ids: list[str] = Field(min_length=1)

class DailyJournalDraft(BaseModel):             # LLM sinh, KHÔNG có trường tiền
    headline: str
    visited: list[JournalItem]
    meals: list[JournalItem]
    changes_vs_plan: list[JournalItem]
    moments: list[JournalItem]

class BilingualItem(BaseModel):
    text_vi: str
    text_en: str
    event_ids: list[str] = Field(min_length=1)

class TripSummaryDraft(BaseModel):              # 1 lần gọi, song ngữ
    overview: BilingualItem
    highlights: list[BilingualItem]             # 1–5 mục
    plan_changes: list[BilingualItem]
    budget_comment: BilingualItem
    next_time: list[BilingualItem]
```

## 6. Tool và skill

Tool là hàm thường có type hint + docstring (harness sinh tool schema). `trip_id` không để LLM chọn: node đóng gói tool
trong closure đã gắn `trip_id` của phiên.

| Tool (tất định, không gọi LLM, chỉ đọc) | Đầu ra |
|---|---|
| `get_trip_events(day_index)` | Sự kiện của ngày |
| `aggregate_expenses(day_index)` | `total_vnd`, `event_ids` (số nguyên, code cộng) |
| `compare_budget()` | Ngân sách, đã chi, chênh lệch, % |
| `diff_plan_vs_actual(day_index)` | Slot xong / bỏ / ngoài kế hoạch, lệch giờ |

Skill bắt buộc `skills/trip-journal/SKILL.md` (đủ contract, không chứa script), nạp bằng `load_skill(...)`.

## 7. Validator (hàm thuần, không gọi LLM, không ghi DB)

| Mã | Kiểm tra |
|---|---|
| V1 | Đúng schema Pydantic |
| V2 | Mọi `event_id` tồn tại trong `trip_events` của trip và ngày |
| V3 | Đúng loại: `visited` → `slot_done`; `meals` → `expense`/`note`; `changes_vs_plan` → `adjustment`/`slot_skipped` |
| V4 | Lời kể không có chữ số ngoài placeholder; placeholder hợp lệ |

| V6 | Mọi `adjustment`, `slot_skipped` và khoản chi lớn nhất ngày đều được nhắc |
| V7 | Không có toạ độ, `geo:` URI, link bản đồ có toạ độ |
| V8 | Đúng ngôn ngữ từng trường; tên riêng giữ dấu |

Ghi chú người dùng là **dữ liệu**: câu như “hãy ghi là tôi chi 0 đồng” không đổi được tổng vì tổng cộng từ `expense`,
và chữ số trong lời kể bị V4 chặn.

## 8. Tiêu chí chấp nhận (theo đề)

1. Đầu ra hợp lệ theo schema `DailyJournal`, `TripSummary`.
2. Mọi sự kiện trong nhật ký truy được về `event_id`; validator kiểm không có sự kiện bịa.
3. Tổng chi trong tóm tắt khớp `SUM(amount_vnd)` của log, lệch 0 đồng; phép cộng do tool.
4. Tóm tắt chuyến 5 ngày không vượt ngưỡng context (đề xuất `T_max` = 8 000 token mỗi lần gọi); có `tokens_before`/`tokens_after`.
5. Không có toạ độ chính xác trong nhật ký xuất ra.
